## 2. Logic Chain
1. **Schema Integrity**: Running `verify_schema.js` confirms PostgREST cache (`PGRST205` avoided) and schema accessibility across public and admin roles.
2. **Constraint Enforcement**: Direct REST API calls attempting invalid foreign keys were rejected by PostgreSQL engine with code `23503`. This proves foreign key constraints are active and enforced at DB level.
3. **Identity Column Mechanics**: The table DDLs use `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. Because they use `GENERATED BY DEFAULT`, explicit primary key values can be inserted (satisfying requirement R1 / M1 explicit PK testing).
4. **Cascading & Referential Integrity**: Deletion of parent entities correctly triggered configured `ON DELETE CASCADE` and `ON DELETE SET NULL` actions without leaving dangling references.

---

## 3. Caveats
1. **Identity Sequence Synchronization for M2 Data Migration**:
   - In PostgreSQL, inserting explicit PK values into an identity column does NOT automatically advance the underlying sequence.
   - When M2 seeds real data with explicit IDs (e.g. technicians `1..120`, appointments `1..1982`, categories `1..7`), subsequent auto-increment inserts (without explicit `id`) will attempt to insert starting from sequence value `1` and crash with duplicate primary key error (`23505`).
   - **Mitigation for M2**: M2 seeding script MUST execute `SELECT setval(pg_get_serial_sequence('table_name', 'id'), (SELECT COALESCE(MAX(id), 1) FROM table_name));` for all identity tables after bulk migration.
